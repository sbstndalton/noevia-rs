# Native model delete (noevia#1318)

`native-model-delete` with `MODEL_MANAGER_MODEL_DELETE_IMPL=rust` serves `POST /api/v1/models/delete`. The default is `python`. The confirmed child (`NOEVIA_NATIVE_MODEL_MANAGER_MODEL_DELETE_CONFIRMED=1`) refuses that route with 503, so model files are only ever deleted by one process. The child gets the same `MODELS_DIR`, `MODELS_INI_PATH`, `MODELS_HOST_PATH` and `MODEL_DOWNLOAD_TARGETS`; a case-folded spelling of any of them, or a `MODELS_DIR` that is not absolute and normalised (or is `/`), keeps Python serving the route with one log line. #1966: the native delete also needs `MODEL_MANAGER_DOWNLOADS_IMPL=rust` (it checks the download table); without it model deletion stays with Python, with one log line.

## Behaviour (`api.delete_models`, `services.delete_gguf`)
- **Body:** FastAPI's `dict` body rules (the shared native reader). `body.get("models") or []` is iterated as Python iterates it: a list's items as `str(item)`, a string's characters, a dict's keys. A value Python cannot iterate is its 500.
- **Phase one:** each key is checked (`bad model key`, `model not found`, reported first). For the first key that names a model, the running containers are read once. A model a running container uses answers 409 for the whole request and nothing is deleted.
- **Holders (`model_holders`):** a command-line argument naming one of the model's files (relative to the models folder, `--x=` forms, `posixpath.normpath`), checked against the mount source when `MODELS_HOST_PATH` is set; or `EMBEDDING_MODEL`, `EMBED_MODEL`, `EMBEDDING_NEXT_MODEL`, `LLM_EMBED_MODEL`, `LLM_EMBED_NEXT_MODEL`, `RERANK_MODEL` (only with `NOEVIA_FEATURE_RAG_RERANK` on) naming its id, stem, file name or a section. `model-loader` and this container (`HOSTNAME`) are skipped. #1668: with the embedding service guarded, its own container and env names pointing at its address are skipped, as the Python child does.
- **Active downloads (#1966, as services#81):** a queued or running download whose destination is one of the model's files or inside the folder the delete may remove (its subdir, or the Hugging Face repository folder) answers 409 for the whole request (`<name> has a download queued or running in its folder: <rel>. Wait for it to finish or cancel it first; nothing was deleted.`), checked again in phase two. A flat model is blocked only by its own files. A `*.gguf.download` file in or below the folder counts as another model, so the whole-folder delete degrades to per file.
- **Delete vs download start (#1972, both sides):** before its download check each model's delete reserves what it may remove (the folder it may remove whole: its subdir or the Hugging Face repository folder; a flat model's own files), until the request ends. A download start whose destination is on or inside a reservation answers 409 (`A delete is removing that folder right now; nothing was queued. Try again when it has finished.`) and queues nothing, for the whole plan. The reservation is taken under the job table's lock, so either the delete sees the new job and refuses, or the start sees the reservation and refuses; neither half-deletes.
- **A model's own stale partial (#1974):** a cancelled or crashed re-download can leave `x/a.gguf.download` with no job. It is not a blocker (no active job), but like any partial it counts as another model, so deleting `x/a.gguf` removes the model's files and keeps the folder `x/` with the stale `a.gguf.download`. This is the safe side and matches Python; remove the leftover by hand (or cancel/clear the download that left it).
- **Native downloads, Python delete:** Python cannot see the native job table, so while any native download is queued or running the front refuses `POST /api/v1/models/delete` with 409 (`A download is queued or running; ...`) before forwarding. Coarser than the per-folder check. Nor can this side see Python's delete reservations, so (#1984) while the delete is forwarded the front holds the whole download table: every download start (also a URL or draft-head start whose plan was already in flight) answers 409 (`A delete is removing that folder right now; ...`) and queues nothing. The request body is read before the table is held (#1994). The hold ends when the child answers or the forward fails; a request dropped mid-forward (client gone, route timeout) keeps it until then. The forward ends at the route's deadline (600 s after the request arrived): at that point the hold is released even if Python is still deleting, since this side cannot see past it.
- **A dropped request (#1983, #1997, #1998):** a client that goes away, or the route's timeout, does not end the work a delete has started, and nothing that work relies on is released early. The native delete keeps its one-at-a-time lock and its folder reservations until its last removal returns. With the embedding service guarded, the embedding hold (which keeps a switch from choosing a model being deleted) is kept just as long: until that last removal returns, or for a forwarded delete until the child answers or the forward fails. That work (the forward, each snapshot and removal) is also registered with the request's admission, so the request's permit (one of the front's 4) comes back only when it has ended; a request that times out answers its 504 once it has. The wait for the embedding hold and a forward under it both end at the route's deadline (600 s after the request arrived), so that 504, the hold, the table hold and the permit all come by the route's budget, also for a delete that waited for the hold first. A native removal already under way is not interrupted (its walks are bounded) and keeps all of it until it returns.
- **Trade-offs of the above:** 4 dropped or timed-out deletes still running can hold every request permit, so meanwhile admitted routes answer 503 `service is busy` (the #1385 trade-off, as for Docker drivers), for at most the route's budget. And while a delete keeps the embedding hold (at most the route's budget, as above), an embedding switch (`PUT /api/v1/embedding-service`) waits for it only its 15 s lock wait and then fails; it can be retried once the delete has ended.
- **Phase two:** each model is looked up again and checked again (a container listing per model, as Python does), then deleted:
  - **Own folder:** a model alone in its folder tree (no other GGUF below, no mount point inside) takes the whole folder, unless the folder is protected.
  - **Per file:** otherwise its parts, plus its companions when no other main model sits beside it; the folder is removed when left empty and not protected.
  - **Hugging Face cache** (`models--o--r/snapshots/<rev>/...`): the links and the blobs only they use, empty folders up to `snapshots/`, and the repository folder once no snapshot is left.
  - **Protected folders:** the models root, a `MODEL_DOWNLOAD_TARGETS` folder, a symlinked folder, a mount point (`os.path.ismount` or `/proc/self/mountinfo`).
- **Answer:** `{"results": [...]}` with `freed` and `freedH` as Python renders them.

## Decisions (technical)
- **No folder fallback (#1964):** neither side falls back from a flat name to a same-named model in another folder any more (services#81 removed Python's fallback); the fixture's `flat-fallback` case answers `not found: dup.gguf` for the second key on both, and `sub/dup.gguf` stays.
- **Docker fails closed:** with no Docker socket file at all, there is nothing to check (as Python). A socket that is there but cannot be read refuses with Python's 409 text. Python treats a socket it cannot connect to as "no Docker" and deletes.
- **No link is followed while deleting:** every stat, listing, unlink and rmdir goes through directory handles opened from the canonical models folder one component at a time with `O_NOFOLLOW`. A folder swapped for a link after the snapshot fails that model ("failed to delete ...") instead of reaching outside. A Hugging Face blob is removed only when its resolved path is inside both the repository folder and the canonical models folder.
- **Refusals:** the snapshot is the kernel-contained reader of the native model detail read. Where it cannot answer exactly (a link leaving the models folder, an ini whose `model =` path cannot be checked for a requested model, bounds) the request answers the native 503 before anything is deleted. Walks are bounded (one million entries, 64 levels); past that a model's deletion fails with a message instead of running unbounded.
- **Error texts:** `OSError` texts are `[Errno n] strerror: 'path'` as Python prints them; for a failure part way through removing a folder the path named may differ from Python's.
- **One at a time:** requests are serialised; Python's threadpool may interleave two deletes.

## Differential evidence
`tools/gen-model-delete-oracle.py` runs the actual services app (pinned `54b8b51`, services#81) on 35 synthetic cases (69 requests): whole folders, shared folders, nested models, download targets, mount points (a fake mountinfo), the Hugging Face cache (shared and dangling blobs, quant folders), links, partial downloads, read-only folders, keys and bodies of every kind, and holders through a fake Docker client (commands, mounts, env names, reranker switch, the embedding guard, a failing socket). Each step records the answer, the whole tree left behind and the number of container listings. The lib test replays every case on every platform; on Linux the integration test replays them through the router with the kernel-contained opener. CI regenerates the fixture and compares it byte for byte.
