# Native stored-token validation (#1318)

`MODEL_MANAGER_TOKEN_TEST_IMPL=rust` selects local validation after a native settings save. It requires `MODEL_MANAGER_SETTINGS_WRITE_IMPL=rust` and compiled `native-token-test`; default `python` retains the private child helper. A selected native test never falls back to the child. Anonymous settings return success without a network request.

The native validator reads the currently stored token with the existing admitted, bounded settings reader and sends it only to the fixed Hub API `/whoami-v2` endpoint. Certificate verification stays enabled; redirects are not followed. The response follows the actual Python validator for names, fullname/unknown fallback, HTTP status messages and the first 120 Unicode characters of a rejected response. Native bounds are a ten-second total network budget and 32 KiB response. Invalid headers, non-text stored values, unsupported declared text encodings, bad success JSON, storage/transport errors and bounds report the existing generic unavailable result. Transport error strings never reach logs or responses, and full token echoes are redacted from upstream messages. These are deliberate refusals relative to Python's unbounded body and dynamic exception text.

Qualification uses actual `hf.validate_token` with a synthetic httpx transport to record nine cases. The Rust tests replay those cases over a real local HTTP peer, check response bounds, Unicode truncation and secret redaction, and prove the settings route answers with its compatibility child unavailable. No real credential, account or external network is used by qualification. The remaining planning helpers, cache mirrors, schema bootstrap and child lifecycle are separate retirement work.
